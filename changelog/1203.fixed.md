`fit()` no longer crashes the interpreter outright on some tables. Modality detection and predict-time dtype coercion both called `pandas.to_numeric` directly on a column; below pandas 3.0, that function has a signed 32-bit integer overflow in its scientific-notation parser, which segfaults on a string like `"8e2569614270"` (mantissa `8`, exponent in `[2**31, 2**32)`, [pandas#63650](https://github.com/pandas-dev/pandas/issues/63650), fixed upstream in pandas 3.0). Below pandas 3.0, parsing now goes through Python's built-in `float` instead, one value at a time, which does not share the bug; pandas 3.0 and later are unaffected and keep using `pandas.to_numeric` directly. Either way, the result is now always `float64`: `pandas.to_numeric` alone narrows to `int64` for a column with nothing to coerce to `NaN` (e.g. `["1", "2", "3"]`), which previously disagreed with the pandas < 3 path.
